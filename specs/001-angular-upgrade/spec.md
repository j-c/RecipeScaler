# Feature Specification: Upgrade Angular & All Dependencies

**Feature Branch**: `001-angular-upgrade`  
**Created**: 2026-02-27  
**Status**: Draft  
**Input**: User description: "Upgrade Angular and all dependencies to current supported versions"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Existing recipes still work after upgrade (Priority: P1)

A user who has bookmarked or shared a recipe URL (containing a base64-encoded JSON payload) opens that link in a modern browser. The recipe renders identically to how it did before the upgrade: name, ingredients table, scaling inputs, serves row, and description all appear and function correctly.

**Why this priority**: If existing URLs break, the core value of the app — shareable, self-contained recipe links — is lost. This is the non-negotiable URL-as-data-store contract from the constitution.

**Independent Test**: Open a known recipe URL (e.g. the default "Manhattans for two") in the upgraded app and verify all content displays and scaling works.

**Acceptance Scenarios**:

1. **Given** a recipe URL generated by the pre-upgrade app, **When** a user opens it in the upgraded app, **Then** the recipe name, all ingredients with measures, and description render correctly.
2. **Given** a rendered recipe, **When** a user changes the scaled value of one ingredient, **Then** all other ingredient scaled values update proportionally.
3. **Given** a recipe with a serves count, **When** a user changes the desired serves value, **Then** all ingredient scaled values update to match the new ratio.
4. **Given** no recipe in the URL, **When** a user visits the base path, **Then** the default recipe ("Manhattans for two") loads automatically.

---

### User Story 2 - Application builds and runs on modern tooling (Priority: P2)

A developer clones the repository, runs `npm install` and `ng build` (or equivalent), and gets a successful production build with zero errors. `ng serve` starts a local dev server that serves the app.

**Why this priority**: A buildable project is the prerequisite for any future feature work. Without it, the upgrade has no value.

**Independent Test**: Run `npm install && ng build` on a clean checkout and verify exit code 0 and a `dist/` output folder with a working app.

**Acceptance Scenarios**:

1. **Given** a fresh clone of the upgraded branch, **When** `npm install` is run, **Then** all dependencies resolve without errors or deprecation-blocked installs.
2. **Given** dependencies are installed, **When** `ng build` is run, **Then** the build completes with exit code 0 and produces output in `dist/`.
3. **Given** dependencies are installed, **When** `ng serve` is run, **Then** a local dev server starts and the app is accessible in a browser.

---

### User Story 3 - Unit tests pass (Priority: P3)

A developer runs `ng test` and all existing unit tests pass against the upgraded framework and test tooling.

**Why this priority**: Tests validate that core logic (scaling, encoding/decoding) is intact. Lower priority than build and runtime because manual verification can substitute in the short term.

**Independent Test**: Run `ng test --watch=false` and verify all specs pass.

**Acceptance Scenarios**:

1. **Given** the upgraded project, **When** `ng test --watch=false` is run, **Then** all unit tests pass with zero failures.

### Edge Cases

- What happens when a recipe URL contains characters that are valid in the old Angular router but handled differently by the new router?
- How does the app behave if `@angular/http` (now removed) is still referenced in source code?
- What happens if the `ng2-sharebuttons` library (or any removed dependency) has no compatible replacement?

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The upgraded app MUST render recipes from base64-encoded JSON URL parameters with functional equivalence to the current version — the same data (name, description, ingredients, serves) and the same interactions MUST be present, but visual styling and layout MAY differ.
- **FR-002**: The ingredient scaling interaction MUST work: changing one ingredient's scaled value MUST proportionally update all other ingredients.
- **FR-003**: The serves scaling interaction MUST work: changing the desired serves MUST proportionally update all ingredient scaled values.
- **FR-004**: Visiting the app with no recipe parameter MUST redirect to the default recipe ("Manhattans for two").
- **FR-005**: The app MUST build successfully with `ng build` (or equivalent) using current supported versions of Angular CLI and Angular.
- **FR-006**: The app MUST run via `ng serve` and be functional in the latest two major versions of Chrome, Firefox, Safari, and Edge.
- **FR-007**: All Angular framework packages MUST be upgraded to the current latest stable version (Angular 21).
- **FR-008**: TypeScript MUST be upgraded to a version supported by the target Angular version (TypeScript >=5.9 <6.1).
- **FR-009**: Build and test tooling (Karma/Jasmine for unit, Protractor for e2e) MUST be replaced with supported alternatives (Vitest for unit, Playwright for e2e) compatible with the target Angular version.
- **FR-010**: Deprecated or abandoned dependencies (`ng2-sharebuttons`, `bootstrap-material-design`, `ts-helpers`, `@angular/http`) MUST be removed or replaced with supported alternatives.
- **FR-011**: The project MUST NOT introduce any new runtime dependencies beyond what is strictly required by the Angular framework upgrade and approved dependency replacements (see Assumptions).
- **FR-012**: When a supported alternative exists that aligns with Angular defaults or community preference, it SHOULD be used as the replacement (e.g. `@angular/common/http` replaces `@angular/http`, `tslib` replaces `ts-helpers`).
- **FR-013**: When a dependency has been discontinued and its feature may be dropped entirely, the decision MUST be confirmed with the project owner before removal.

### Assumptions

- The `ng2-sharebuttons` share button functionality will be removed entirely during this upgrade (no replacement). Social sharing will be reintroduced in a future iteration using the native Web Share API.
- `bootstrap-material-design` styling will be replaced with Angular Material (`@angular/material`). Visual parity with the old design is NOT required; functional equivalence (same data displayed, same interactions) is sufficient.
- The Protractor e2e test runner (deprecated) will be replaced with Playwright. E2e tests MUST be compatible with GitHub Actions (no workflow file required in this feature; CI pipeline is a separate concern).
- The base64 JSON encoding scheme (`btoa`/`atob` of `JSON.stringify`) will continue to work as-is since it relies on browser APIs, not Angular.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: `ng build` completes with exit code 0 and zero errors on a clean checkout.
- **SC-002**: The default recipe renders in under 3 seconds in desktop Chromium with no network throttling (local `ng serve` or production build).
- **SC-003**: All existing unit tests pass with zero failures.
- **SC-004**: A recipe URL generated by the pre-upgrade app displays correctly in the upgraded app (backward-compatible URL contract).
- **SC-005**: The total number of runtime dependencies is equal to or fewer than the current count (13 packages).
- **SC-006**: No dependency in `package.json` has a known critical or high severity vulnerability (per `npm audit`).
